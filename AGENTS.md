# AGENTS.md — правила работы над проектом VoltGroup

Этот файл читается **первым** перед любой задачей. Он задаёт правила, ограничения и обязательный режим отчётности. Файл описывает **как** работать; что именно осталось сделать — в [AGENT_STATE.md](AGENT_STATE.md), перечень проблем — в [AUDIT.md](AUDIT.md).

**Проект:** статический сайт электромонтажных работ + калькулятор сметы + Telegram-бот с мини-CRM.
**Стек:** HTML/CSS/vanilla JS (без сборки и фреймворков), Python 3 + Flask + gspread + Google Таблицы, хостинг фронтенда — обычный веб-сервер, бэкенд — Render.
**Язык:** весь текст интерфейса, комментарии, коммиты и документация — **на русском**.

---

## 0. Стартовый протокол — обязателен в начале каждой сессии

1. **Прочитать три файла:** этот, [AGENT_STATE.md](AGENT_STATE.md), при необходимости [AUDIT.md](AUDIT.md).
2. **Определить точку старта** из блока «Текущий фокус» в `AGENT_STATE.md`. Не начинать новую задачу, если предыдущая помечена как «в работе» — сначала завершить или явно зафиксировать, почему она отложена.
3. **Объявить план** пользователю до правок: какие пункты `AUDIT.md` берёшь, какие файлы тронешь.
4. **Для задач из 3+ шагов** — вести список через инструмент задач, синхронизируя его с реальным прогрессом.

## 1. 🔴 ГЛАВНОЕ ПРАВИЛО: обязательная фиксация результата

Это требование приоритетнее всех остальных. Агент **обязан** вести журнал в [AGENT_STATE.md](AGENT_STATE.md).

### 1.1. Когда писать

| Событие | Действие |
|---|---|
| Начало задачи | Обновить «Текущий фокус»: дата, что делаю, ожидаемый результат |
| Завершён **каждый** смысловой шаг | Дописать запись в «Журнал сессий» по шаблону из §7 |
| Изменился статус пункта аудита | Сразу отметить в таблице прогресса и в списке этапа |
| Обнаружена новая проблема | Добавить пункт в `AUDIT.md` **и** упомянуть в журнале |
| Задача упёрлась в невозможность | Записать в «Блокеры»: что именно мешает, что нужно от человека |
| Завершение сессии | Итоговая запись: где остановился и **что делать дальше** |

### 1.2. Что обязательно содержит каждая запись

1. **Что сделано** — конкретное действие, а не «поработал над задачей».
2. **Какие файлы изменены** — полные пути и номера строк или диапазоны.
3. **Как проверено** — чем именно убедился, что работает. «Должно работать» не является проверкой.
4. **Где остановился** — точная точка: функция, строка, файл, пункт плана.
5. **Что осталось** — пронумерованный список следующих шагов, начиная с самого близкого.

### 1.3. Формат «что осталось»

Пишется как продолжение работы, а не как общее пожелание:

```
Следующие шаги:
1. server.py — добавить проверку token в get_status (строки 317-351), брать из query-параметра `t`.
2. client/index.html — передать t из URL в fetch на строке 310.
3. server.py — генерация токена при создании объекта (строки 551-564).
4. Проверка: открыть кабинет без токена → 404; с токеном → данные.
```

### 1.4. Запрещено

- Помечать пункт выполненным, если он не проверен запуском или осмотром.
- Начинать новую задачу, не дописав журнал по предыдущей.
- Записывать «всё сделано» без указания конкретных файлов и строк.
- Удалять старые записи журнала — история только дополняется.
- Оставлять состояние проекта только в своей памяти: если сессия оборвалась, всё нужное должно быть в `AGENT_STATE.md`.

## 1-бис. Протокол передачи: цикл работы по карточке

Реализация всех этапов идёт через карточки в [`tasks/`](tasks/README.md). Цикл строго такой — **по одной карточке за подход**:

1. **Выбрать карточку** со статусом ⏳ из [`tasks/README.md`](tasks/README.md), соблюдая порядок внутри этапа. Если статус предыдущей — 🔄 или 💬, сначала закрыть её или зафиксировать причину переноса.
2. **Прочитать карточку целиком.** Не начинать, если в ней есть блокирующий вопрос (💬) — такой пункт требует решения заказчика.
3. **Внести правки** строго по разделу «Шаги». Не расширять объём: посторонние улучшения «заодно» — нарушение (§2.5).
4. **Проверить** командой из раздела «Проверка» карточки. Проверка обязательна; при невозможности — прямо написать, что не проверено и почему.
5. **Отчитаться в трёх местах:**
   - в карточке: `**Статус:**` — на `✅ завершено (дата)`;
   - в [`tasks/README.md`](tasks/README.md): статус в таблице этапа;
   - в [`AGENT_STATE.md`](AGENT_STATE.md): запись в «Журнал сессий» по шаблону §7 и обновление таблицы прогресса этапа.
6. **Предложить коммит** по формату §6, с номером карточки в теле.

### Формат статуса в карточке

Первая строка статуса — ровно один маркер, дальше пояснение:

```
**Статус:** ⏳ не начато
**Статус:** 🔄 в работе (дата, где остановился)
**Статус:** ✅ завершено (дата)
**Статус:** ⏸ отложено (причина, условие возврата)
**Статус:** 💬 ждёт решения заказчика (что именно решить)
```

### Что писать в отчёте по карточке

Минимум: номер карточки, какие файлы и строки изменены, **вывод команды проверки** (не пересказ), что осталось непроверенным. Утверждение «работает» без вывода команды или сценария не принимается (§3).

### Особенности этого проекта

- **Публикация = коммит в `main`.** Сайт на GitHub Pages публикуется из ветки `main` сразу после пуша, промежуточной среды нет. Значит коммит и пуш — это выкладка в прод: не коммитить полусырое, не коммитить чужие незавершённые правки, не оставлять в истории утверждений, которые не проверялись.
- **Репозиторий публичный.** Секреты, ключи и содержимое Google Таблиц в код и документацию не попадают никогда (§2.2).
- **Ведение `AGENT_STATE.md`.** Файл общий для всех исполнителей. Если с ним параллельно работает другая сторона, изменения теряются: файл перезаписывается между чтением и записью. Правило: перед правкой перечитать файл, после правки убедиться, что запись сохранилась; при конфликте — не перезаписывать чужое, а дописывать.
- **Карточки 035–044 (SEO)** частично требуют действий в панелях Яндекса и Google. Агент их выполнить не может — в таких карточках явно указано «действие человека». Задача агента там: подготовить тексты, привести данные в коде в порядок и зафиксировать результат, который сообщит заказчик.

## 2. Правила проекта, которые нельзя нарушать

### 2.1. Данные и источники истины

- **Цены — только** в [static/data/prices.json](static/data/prices.json). Никогда не хардкодить прайс в HTML. Страницы `index.html`, `install/index.html`, `engineering/index.html` и `estimate.html` берут данные оттуда.
- **Галерея — только** в [gallery/gallery-config.json](gallery/gallery-config.json). Все 14 записей ссылаются на `.webp`; добавляя карточку, класть файл в `gallery/` и указывать относительный путь.
- **Реквизиты исполнителя** (ФИО, ИНН, телефон) сейчас продублированы в разметке. При правке менять **все** вхождения сразу: [estimate.html](estimate.html) (генераторы документов), футеры страниц, [client/index.html](client/index.html).
- **База расчёта в документах должна совпадать.** Если меняешь `worksFinal`/`grandTotal`/скидку — проверь все четыре документа: договор, КП, акт, смета (пункты аудита № 10, 11, 30).

### 2.2. Безопасность

- **Никаких секретов в репозитории.** Токены, `GOOGLE_CREDENTIALS`, `SHEET_URL` — только через переменные окружения. **Репозиторий публичный** ([github.com/mmmatveyz/voltgroup](https://github.com/mmmatveyz/voltgroup)), поэтому утечка необратима: достаточно одного коммита. Добавить `.env`, `.env.*`, `logs/`, `debug.log` в [.gitignore](.gitignore) — этого там пока нет ([tasks/008](tasks/008-env-example.md)).
- **Не ослаблять проверку `TELEGRAM_SECRET_TOKEN`** ([server.py:361](server.py#L361)) и не менять `ALLOWED_ORIGINS` на `*`.
- **`html.escape()` в боте** для любых данных из таблицы оставлять на месте.
- **`escapeHtml()` в JS** ([estimate.html:492](estimate.html#L492)) обязателен для всего, что попадает в `innerHTML` или `document.write`. Пользователь вводит ФИО и адрес — эти данные уходят в генерируемые документы.
- **Не добавлять небезопасные источники в CSP.** Политика продублирована в `<meta>` на каждой странице — правишь в одном месте, проверь остальные.
- **Клиентский кабинет** — данные клиента, они не должны попадать в публичные ответы. Сейчас `/get-status` без аутентификации — это пункт № 1 аудита, исправление в приоритете.

### 2.3. Бэкенд

- **Один воркер.** `user_states` ([server.py:111](server.py#L111)) и лимиты ([server.py:50](server.py#L50)) живут в памяти процесса. До перехода на внешнее хранилище запускать строго `-w 1 -k gthread`. Не «оптимизировать» это на несколько воркеров, не перенеся состояние.
- **Google Sheets — дорогой ресурс.** `ws.find()` читает всю колонку. Не добавлять новые вызовы в циклы и обработчики кнопок (пункт № 15 аудита).
- **Любое изменение схемы таблицы** (новая колонка) синхронно править в `COLUMNS_MAP` ([server.py:72](server.py#L72)), в `build_object_view`, `get_status` и в `client/index.html`.
- **Сообщения об ошибках** не должны содержать стектрейсы и внутренние пути — они уходят в Telegram.

### 2.4. Фронтенд

- **Без сборки.** Не вводить npm, webpack, TypeScript, фреймворки. Только обычные `.html`, `.css`, `.js`, подключаемые тегами.
- **Без внешних CDN**, кроме уже используемых: Google Fonts, Яндекс.Метрика, виджет Яндекс.Справки. Всё остальное — локально.
- **Кэш-бэстинг:** при любой правке [static/css/style.css](static/css/style.css) обязательно синхронно обновлять версию `?v=` **на всех 10 страницах** проекта (актуальная: `v=2.4`, отсутствие рассинхрона проверяется автоматически в `tools/check.py`).
- **Инлайновые скрипты и стили допустимы** (так устроен проект), но помнить: из-за них CSP содержит `'unsafe-inline'` и не может быть ужесточён без выноса кода в файлы.
- **Пользовательские данные — только через `textContent`** либо `escapeHtml()`. Никогда не собирать HTML конкатенацией неэкранированных значений.
- **Доступность:** сохранять `focus-visible`, `aria-*`, `prefers-reduced-motion` — они добавлены осознанно.

### 2.5. Стиль правок

- **Минимальное вмешательство.** Править то, что просили, не переформатировать соседний код, не переименовывать переменные, не менять отступы в чужих блоках.
- **Комментарии — на русском**, по делу, без пересказа кода.
- **Изменения делать атомарно** — одна задача, один логичный набор правок. Не смешивать исправление бага и рефакторинг.
- **Не создавать новые файлы**, если задачу решает правка существующего. Исключение — файлы, прямо требуемые аудитом (`render.yaml`, `.env.example`, `static/js/config.js`).
- **Большие файлы не переписывать целиком.** [static/css/style.css](static/css/style.css) — 2692 строки, [static/js/documents.js](static/js/documents.js) — 877, [static/js/estimate.js](static/js/estimate.js) — 1003. Использовать точечные правки. После разбиения `estimate.html` (задача 018) держать модульность и не возвращать логику обратно в HTML.

## 3. Обязательная проверка результата

После каждого изменения — убедиться, что оно работает.

**Главная команда комплексной проверки (обязательна перед отчётом и коммитом):**
```bash
python tools/check.py
```
Скрипт проверяет синтаксис Python, валидность всех JSON-конфигов, физическое наличие и формат изображений галереи, а также запускает модульные тесты: сумму прописью (`tools/test_money.js`), базу расчёта (`tools/test_doc_totals.js`), математику сметы (`tools/test_estimate_calc.js`) и смоук-тесты четырёх документов (`tools/test_doc_smoke.js`).

Минимум по отдельным компонентам:

| Что изменено | Чем проверять |
|---|---|
| Комплексный прогон | `python tools/check.py` — полный цикл всех автоматических проверок |
| `server.py` | `python tools/check.py` или `python -c "import ast,sys; ast.parse(open('server.py',encoding='utf-8').read())"` |
| HTML / CSS / JS | Открыть страницу через локальный HTTP-сервер (`tools/serve.cmd` или `python -m http.server`), а не по `file://` |
| `prices.json`, `gallery-config.json` | `python tools/check.py` — валидность JSON и файлов галереи |
| Генераторы документов / сметы | `node tools/test_doc_smoke.js` и `node tools/test_estimate_calc.js` |
| Любые правки контента | Проверить, что не появилось битой кодировки (кириллица, `₽`, эмодзи) |
| Изменения схемы данных | Синхронно проверить `server.py`, `client/index.html` и структуру таблицы |

**Запрещено** писать в журнал «проверено», если использовался только просмотр глазами. Указывай конкретную команду или сценарий с её выводом.

## 5. Приоритеты и план работ

Источник — [AUDIT.md](AUDIT.md). Этапы выполняются по порядку; внутри этапа — по номерам.

| Этап | Тема | Пункты аудита |
|---|---|---|
| **1** | Безопасность и работоспособность | 1, 2, 3, 4, 5, 18, 19, 33 |
| **2** | Скорость и конверсия | 6, 7, 8, 16, 28, 31 |
| **3** | Юридические документы и расчёты | 10, 11, 14, 22, 30 |
| **4** | Устойчивость, UX, комплаенс | 9, 12, 13, 15, 17, 20, 21, 23–27, 29, 32, 34 |
| **5** | SEO и видимость в поиске | задачи [035–044](tasks/README.md) в `tasks/` — добавлены после аудита |

**Порядок внутри этапа:** сначала то, что убирает утечку данных или тихий отказ (данные теряются без сообщения об ошибке), затем удобство, затем косметика.

**Про этап 5 (SEO).** Техническая часть — в коде (`sitemap.xml`, разметка, вес страниц, контент). Внешний контур (Яндекс.Вебмастер, Яндекс.Бизнес, Google, каталоги) выполняет человек в веб-интерфейсах — агент туда доступа не имеет. От агента требуется: не ломать существующую разметку (`canonical`, JSON-LD, `robots.txt`; `noindex` — **только** на `client/index.html`), держать `sitemap.xml` в соответствии с реальными URL и фиксировать в журнале результаты, которые сообщает человек.

**Что не делать без отдельного запроса:**
- Не переписывать README целиком, если задача — другое (но пункт № 4 обязателен к выполнению).
- Не проводить рефакторинг CSS ради уменьшения `!important` без задачи.
- Не менять дизайн, тексты, формулировки документов «заодно».
- Не добавлять запреты на индексацию (`Disallow` в `robots.txt`, `noindex` в `<meta name="robots">`) для страниц, которые должны находиться в поиске: это прямой вред для цели «сайт должен появляться в поиске».

## 6. Формат коммитов

После завершения логического блока — предложить коммит. Сообщение на русском, в стиле существующей истории (`feat:`, `fix:`, `chore:` + суть):

```
fix(security): токен в ссылке кабинета и проверка в /get-status

- server.py: генерация token при создании объекта, проверка в get_status
- client/index.html: передача t из query в запрос статуса
- Закрывает пункт № 1 AUDIT.md
```

В теле коммита **указывать номер пункта аудита** — это связывает историю с планом.

## 7. Шаблоны записей

### Запись в «Журнал сессий» файла `AGENT_STATE.md`


## 8. Чек-лист завершения сессии

Перед тем как ответить пользователю в последний раз, проверить:

- [ ] Запись в журнал `AGENT_STATE.md` добавлена и содержит все пять обязательных элементов (§1.2).
- [ ] «Текущий фокус» отражает реальное положение дел.
- [ ] Отмечены выполненные пункты аудита; при необходимости в `AUDIT.md` они помечены как закрытые.
- [ ] Блокеры выписаны с описанием, что требуется от человека.
- [ ] «Что осталось» сформулировано как готовые к выполнению шаги с файлами и строками.
- [ ] Все изменённые файлы сохранены, ничего не осталось в недописанном виде.
- [ ] Предложено сообщение для коммита, если изменения завершены.
