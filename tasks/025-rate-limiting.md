# Задача 025 — Ревизия лимитов запросов

**Пункт аудита:** № 25 · из [AUDIT.md](../AUDIT.md)
**Статус:** ✅ завершено (07.10.2026)
**Файлы:** `server.py`, `index.html`, `install/index.html`, `engineering/index.html`, `contacts/index.html`, `client/index.html`, `tools/check.py`

## Проблема

Дефолтные лимиты `200 per day, 50 per hour` ([server.py:49](../server.py#L49)) считаются по IP. В офисах и ЖК с общим NAT клиенты делят один адрес — часовой лимит может исчерпаться соседями, и форма отдаст 429 без объяснения. `/ping` не ограничен вовсе (см. задачу 015).

## Шаги

1. Развести лимиты по маршрутам: `/send-message` — строгий (защита от спама), `/get-status` — мягче, `/ping` — отдельный (задача 015).
2. Вернуть при 429 понятный JSON с текстом, а не общий ответ — сейчас клиент покажет невнятную ошибку.
3. На стороне клиента: обработать 429 отдельным сообщением «Слишком много запросов, попробуйте через минуту» с резервным каналом связи.
4. Учесть, что при нескольких воркерах лимиты становятся «на воркер» — держать один воркер (задача 002).
5. Не полагаться на `X-Forwarded-For` как на единственный идентификатор: `ProxyFix` доверяет заголовкам, значит IP можно подделать при прямом доступе к сервису.

## Критерий готовности

Честный пользователь никогда не упирается в лимит при обычном поведении; при превышении получает понятное сообщение; зацикленные вызовы ограничены.

## Проверка

- `for /l %i in (1,1,60) do curl -s -o NUL -w "%{http_code} " http://127.0.0.1:8000/get-status?id=1` → после достижения лимита приходит 429 с JSON.
- Отправка формы 6 раз подряд с одного IP → 6-я отдаёт понятное сообщение.
- Проверить, что обычный сценарий (одна заявка, один просмотр кабинета) не задевает лимиты.
