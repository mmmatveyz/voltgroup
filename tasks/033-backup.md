# Задача 033 — Резервное копирование данных

**Пункт аудита:** № 34 · из [AUDIT.md](../AUDIT.md)
**Статус:** ⏳ не начато
**Файлы:** новый скрипт (например, `tools/backup.py`), настройка расписания на хостинге

## Проблема

Вся бизнес-информация (объекты, суммы, оплаты, этапы, ссылки на фото) хранится в Google Таблице. В проекте нет ни скрипта экспорта, ни упоминания о бэкапах. Google даёт версионирование, но восстановление после ошибочного действия бота (например, случайного обнуления оплаты) — ручная работа по истории изменений.

## Шаги

1. Написать `tools/backup.py`: читает `sheet1` через сервисный аккаунт (те же `GOOGLE_CREDENTIALS`, `SHEET_URL`) и сохраняет снимок в CSV или JSON с датой в имени файла.
2. Хранить 30 последних снимков, старые удалять; каталог бэкапов не коммитить (добавить в `.gitignore`).
3. Настроить ежедневный запуск: cron на сервере, планировщик хостинга или Apps Script внутри таблицы.
4. Добавить проверку успешности: если снимок не создался или пустой, отправить алерт (переиспользовать `notify_admin` из задачи 032).
5. Описать процедуру восстановления в `docs/DEPLOY.md` или отдельном `docs/RESTORE.md`: как из снимка вернуть строку объекта.

## Критерий готовности

Ежедневный снимок данных создаётся автоматически; есть документированная процедура восстановления.

## Проверка

- `python tools/backup.py` → файл создан, число строк совпадает с таблицей (`get_all_values()`).
- Проверить содержимое: заголовки, все объекты, суммы, токены.
- Настроить запуск → через сутки проверить, что появился новый снимок.
- Смоделировать сбой (неверные права) → приходит алерт.
- Провести тренировку восстановления на тестовом объекте в отдельном листе.

## Примечание

Бэкап бесполезен без проверенной процедуры восстановления — тренировка обязательна.
