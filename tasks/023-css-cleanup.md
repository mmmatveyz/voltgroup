# Задача 023 — Разбирать `!important` и инлайн-стили постепенно

**Пункт аудита:** № 21 · из [AUDIT.md](../AUDIT.md)
**Статус:** ⏳ не начато (низкий приоритет, делать фоном)
**Файлы:** `static/css/style.css`, разметка страниц

## Проблема

В [static/css/style.css](../static/css/style.css) 62 вхождения `!important`, плюс много инлайновых `style="..."` в разметке (особенно в `estimate.html`). Это признак конфликтующих правил и растущей специфичности: любой рефакторинг становится хрупким, тёмная тема и адаптив ломаются от неожиданных мест.

## Шаги

1. Разобрать случаи по происхождению: `!important` из-за инлайнового стиля, из-за конфликта селекторов, из-за порядка подключения, «на всякий случай».
2. Вынести повторяющиеся наборы инлайновых свойств в классы (например, `cta-full-width`, `muted-note`).
3. Для каждой группы: убрать `!important`, проверить визуально на desktop и mobile, закоммитить отдельно.
4. Не делать всё сразу — по 5-10 случаев за подход, иначе регрессию не отследить.
5. Упорядочить слои: `reset → base → layout → components → utilities`.

## Критерий готовности

Число `!important` уменьшается от подхода к подходу без визуальных регрессий. Конечная цель — единицы, а не 62.

## Проверка

После каждого подхода:

- `python -m http.server` → пройти все страницы на ширине 1920, 768, 375 px;
- сверить ключевые экраны: hero, прайс, галерея, формы, футер, модальное окно мастера, калькулятор;
- проверить, что тёмная тема и неоновые акценты без изменений;
- фиксировать в журнале число до/после: `!important` было N, стало M.

## Примечание

Это единственная задача, которую не стоит брать «наскоком» вместе с другими: слишком велик риск незамеченной визуальной регрессии.
