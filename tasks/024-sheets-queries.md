# Задача 024 — Уменьшить число обращений к Google Sheets

**Пункт аудита:** № 15 · из [AUDIT.md](../AUDIT.md)
**Статус:** ⏳ не начато
**Файлы:** `server.py`

## Проблема

`ws.find()` в gspread выгружает всю колонку и ищет в ней. На одно нажатие кнопки приходится 2-6 таких вызовов: [server.py:210](../server.py#L210), [341](../server.py#L341), [444](../server.py#L444), [464](../server.py#L464), [484](../server.py#L484), [543](../server.py#L543), [607](../server.py#L607). Плюс `build_objects_list` читает всю таблицу ([server.py:183](../server.py#L183)). Отсюда отклик 1-3 секунды на нажатие и расход квоты Google API (ориентировочно 60 чтений в минуту на пользователя).

## Шаги

1. В начале обработки вебхука один раз получать снимок `ws.get_all_values()` и работать с ним, а не вызывать `find()` многократно.
2. Построить словарь `{obj_id: row_number}` для точного поиска (это же закрывает задачу 006 — частичное совпадение).
3. Кэшировать снимок в пределах одного запроса; при записи обновлять и снимок, и таблицу.
4. `build_objects_list` перевести на тот же снимок вместо отдельного чтения.
5. Для `get_status` (клиентский кабинет) оставить одиночное чтение строки, если снимок всей таблицы окажется дороже.
6. Не кэшировать данные между запросами без инвалидации — иначе мастер увидит устаревший прогресс.

## Критерий готовности

Одно нажатие кнопки — не более одного чтения таблицы; отклик заметно быстрее; расход квоты снижен.

## Проверка

- Замер: засечь время обработки нажатия «💰 Внести оплату» до и после (в логах или по секундомеру).
- Пройти сценарий: список объектов → карточка → прогресс → этап → оплата → возврат в список.
- Проверить, что параллельные изменения (правка ячейки вручную в момент работы бота) не приводят к потере данных.
- В логах не должно появляться `429` от Google API при обычной работе.
